# OpenAI 보완 후 회귀 평가

측정일: 2026-10-21. 문서 대조일: 2026-10-22. 최초 평가에서 확인한 실패를 보완한 뒤 **같은 24문항·40시나리오**를 다시 사용했다. 지원 18문항의 실행 시나리오는 34개이며 미지원은 6문항이다. 이 결과는 이미 확인한 문항의 회귀 평가로, 독립된 미관측 holdout 성능이 아니다. 수치·실패·소스 해시는 당시 원자료를 유지한다.

생성은 `gpt-4o-mini`, 보고는 `gpt-4o`, temperature는 0이다. 각 회차는 새 임시 저장소를 사용하며, 문항·관측 fixture·런북·카탈로그는 최초 평가와 같다. 보완한 workflow만 `--mode workflow --report-mode full --evaluation-role regression`으로 재측정했다. 최초 baseline은 다시 실행하지 않았으며 [초기 비교 결과](workflow_openai_results.md)를 보존했다.

## 1차 보완(v2)

| 지표 | 최초(v1) | 1차 보완(v2) |
|---|---:|---:|

| 지원 시나리오 경로 일치 | 27/34 | 30/34 |

v2는 순차·조건 보존 검사를 통합했고, 미지원 6문항은 생성 모델 호출 전에 전체 거절했다. 그러나 최종 승인이 최초 후보보다 낮은 이유를 다음과 같이 확인했다.

- `holdout_ref_second`: 조건 예시에만 있던 공통 후속 런북을 추가했다. 첫 후보의 미등록 자원을 거절하자 수정 후보는 다른 등록 런북으로 바꾸어 불필요한 단계를 유지했다. 의도 검사에서 최종 차단됐다.
- `holdout_empty_then_next`: 요청의 반대 조건과 분기를 교환해 실행 의미가 같은 후보를 만들었지만, 원문 연산자를 강제하던 의도 검사에서 두 번 거절했다. **검증기의 오탐**이다.

지원 보고 30개를 수동 검토했을 때 허위 운영 변경 완료 주장은 발견하지 못했다. 다만 조건 지표를 메모리에서 CPU로 잘못 설명하거나, 수집한 현재값을 한계 항목에서 미확인으로 쓰거나, 런북 권고의 전제를 다르게 붙인 사례가 있었다. 이는 한정된 수동 검토이며 보고 사실성 점수가 아니다.

v2 실측은 모델 **50회·126,190토큰**이다. 생성 20회·64,132토큰, 보고 30회·62,058토큰이며 모두 공급자가 보고한 사용량이다. 실패 때문에 실행하지 않은 시나리오도 있어 비용·속도 우위를 주장하지 않는다.

## 2차 보완(v3, OpenAI 평가)

| 지표 | 최초(v1) | 1차 보완(v2) | 2차 보완(v3) |
|---|---:|---:|---:|
| 최초 후보 의미 일치 | 13/18 | 17/18 | **18/18** |
| 승인된 최종 절차 의미 일치 | 13/18 | 16/18 | **18/18** |
| 지원 시나리오 경로 일치 | 27/34 | 30/34 | **34/34** |
| 지원 시나리오 추가·중복 조회 | 1회 | 0회 | **0회** |
| 미지원 요청의 명시적 거절 | 3/6 | 6/6 | **6/6** |
| 미지원 요청 도메인 조회 | 4회 | 0회 | **0회** |

v3는 조건 예시의 불필요한 공통 후속 단계를 제거하고, 원문 밖 노드를 다른 자원으로 치환하지 않고 삭제하도록 수정 규칙을 보강했다. 의도 검사는 비교 연산자 반전과 양분기 전체 교환을 사본에서 정규화해 허용한다. 동일 시스템의 복수 관측 이후 조건 참조는 회차를 잘못 연결할 수 있어 지원 범위에서 명확히 거절한다. 이 추가 경계는 독립 자동화 테스트로 검증했으며 이번 24개 문항에는 해당 복수 관측 요청이 없다.

v3의 18개 지원 요청은 모두 최초 한 번의 생성으로 승인됐다. 34개 지원 실행은 보고까지 완료됐고, 미지원 6개는 생성 모델과 도메인 조회 모두 0회였다. 원본 정의를 저장·다시 읽었으며, 같은 문항의 후속 시나리오에는 저장된 정의를 새 관측값으로 실행했다. 무효 AST의 조회 전 차단 **12/12**도 유지된다.

해당 회차의 전체 자동화 검증은 Python **357개**, Node **42개** 통과다. v1·v2·v3의 문항·fixture·카탈로그·런북 해시 및 모델 설정이 같음을 확인했다. 소스 해시는 평가기가 수집한 `agent/`, `prompts/`, `eval/`의 코드로 계산한다. 이후 Ollama 생성 모델 분리와 오류 표시는 별도 점검이며 이 OpenAI 회차의 측정 범위에 넣지 않는다.

소스 SHA256: `ccde0b73875af6dec41001b64b56e81ad5b27c356b9170cc4e9d6385f78c72cc`.

이후 일반 진단의 응답 정체 수정으로 현재 소스는 이 평가 시점과 달라졌다. 이 표는 위 해시의 과거 회귀 측정이며 수정 후 성능을 재측정한 결과가 아니다.

### 보고의 남은 한계

실행 경로 34/34와 `report_valid=true`는 자유 서술 보고가 모두 정확하다는 뜻이 아니다. 수동 검토에서 다음과 같은 명확한 모순이 남았다.

지원 보고 34개 전체를 자료·trace와 수동 대조한 범위에서는 허위 운영 변경 완료, 실측 숫자 변조, 조건 지표 혼동, 선택 분기 뒤집힘을 발견하지 못했다. 이 점검은 완전한 사실성 판정이나 정확도 점수가 아니다.

- `dev_cpu_ge/below`: 메모리 55.0%를 수집·보고했지만 “현재 메모리가 90% 이상인지 미확인”이라고 썼다. 수집값으로 해당 비교가 거짓임을 알 수 있다.
- `holdout_memory_ne/equal`: CPU 42.0%도 수집했지만 보고는 CPU 사용률을 확인하지 않았다고 썼다.

일부 보고의 “추가 확인하지 않았다”는 표현은 실제 현재값 미수집과 별도 조회 미실시를 혼동하게 하고, 런북의 특정 권고 조건을 전체 조치의 불필요성으로 일반화하는 표현도 남았다. 당시 v3의 보고 근거 검사는 명시적 변경 완료 주장과 일부 현재값 부정 표현에 한정됐다. 모든 수치·미수집 주장·권고 전제를 전수 검증하는 판정기가 아니었다. 현재의 관측·분기 코드 출력과 문단 참조 요약은 이후 별도로 추가한 계약이다.

이번 결과는 두 번의 보완에 사용한 같은 문항의 단회 회귀 측정이다. **100%를 새 요청의 정확도나 전체 보고 사실성으로 일반화하지 않는다.** 남은 검증 과제는 새로운 표현·지원 경계를 다루는 미관측 문항과 현재 요약의 근거 일치다. 복합·중첩 조건은 현재 지원 범위에 포함되지 않으며 정확한 거절을 확인할 대상이다.
