# 조건부 워크플로 보고 정확성 보완

적용일: 2026-10-21. 범위는 조건부 워크플로의 보고 경로다. 일반 진단의 자동 런북 추가 정책과 자연어 컴파일러는 이번 변경 대상에 포함하지 않았다.

<!-- [추가] 적용 당시 연동 기록과 현재의 외부 호출 없는 재검증을 분리한다. -->
현재 코드 재검토·자동화 재검증일: **2026-10-22**. 아래 Ollama 1건은 2026-10-21의 연동 기록이며 이번 점검에서 다시 호출하지 않았다. OpenAI의 과거 회귀 평가 역시 현재 보고 계약의 재측정으로 바꾸어 해석하지 않는다.

## 해결한 문제

`web-01`이 healthy여서 CPU 런북을 건너뛰었는데 모델이 “현재 런북 조회는 완료되었다”고 설명했다. 또 `status != healthy`가 거짓인 경로를 설명하면서 연산자를 생략해 모순처럼 읽혔다. 실행 기록을 모델에 제공하고 지시하는 방식만으로는 해당 오류를 막지 못했다.

이제 관측값·조건·조회 여부는 코드에서 출력한다. 런북을 읽었을 때만 모델이 실제 문단을 요약한다.

## 코드와 동작

| 파일 | 역할 |
|---|---|
| `agent/workflow/report_content.py` | 완료 trace와 자료를 연결해 수치·알림·시각·조건식·분기·조회 횟수·건너뜀 출력. 실제 런북의 문서·문단 ID 생성과 구조화 요약 검사 |
| `agent/workflow/report_prompting.py`, `prompts/workflow_report.txt` | 모델에는 실제 런북의 문단·ID와 수정 피드백만 전달. 질문·모니터링·조건 trace는 요약 입력에서 제외 |
| `agent/workflow/graph.py` | 런북 0건이면 보고 모델 0회. 조회 사실을 먼저 보존하고, 요약 검증 후 최종 보고를 합성. 미검증 JSON의 답변 스트림 중계 차단 |
| `agent/workflow/models.py` | 조회 성공 시 코드로 만든 `facts_report` 제공. 요약 실패 시에도 사용 가능 |
| `agent/fake_llm.py` | fake도 문서·문단 참조 JSON 반환. 원본 일반 진단의 `write()` 동작 유지 |
| `web/workflow.js` | 사실 보고·0회 모델 호출 표시. 요약 실패 시 최종 확정과 구분해 확인된 조회 결과 표시 |
| `eval/run_workflow_eval.py` | 새 보고 계약과 baseline/workflow의 서로 다른 전송 범주를 manifest·미리보기에 기록 |

모델의 출력은 다음 구조다. `source_id`는 실제 읽은 런북 순서, `block_id`는 해당 문서의 문단 ID다. 각 런북마다 문단 하나를 골라 요약하는 계약이며 모든 문단을 요약했음을 검증하지는 않는다. 같은 문서를 여러 번 읽으면 각 조회에 별도 자료 ID를 부여한다.

```json
{"summaries":[{"source_id":"runbook_001","block_id":"block_001","summary":"런북은 CPU가 90%를 넘고 지속되면 확장을 권고한다."}]}
```

추가 필드·존재하지 않는 자료/문단·중복/누락 문서·공백 요약·모델 제어 표기·근거 문단에 없는 숫자는 반려한다. 기존의 한정된 허위 운영 변경 완료 검사도 요약에 적용한다. 원문은 모델이 작성하지 않으며 서버가 지정 문단 전체를 가져와 전제조건과 함께 표시한다. 문단은 빈 줄 기준이며, 문단 안의 여러 절차는 함께 보존한다.

모델 응답의 JSON·문단 참조·종료 상태 등에 대한 검증이 실패하면 요약만 최초 시도를 포함해 최대 세 번 작성한다. 모델 통신 오류·명시적 거절·전체 시간 초과는 이 재작성 루프를 계속하지 않고 실패한다. MCP를 다시 조회하지 않는다. 기본 120초의 전체 실행 제한은 조회와 모든 요약 시도가 공유한다. `AnswerToken`에는 검증을 통과한 서버 생성 보고를 한 번만 전달한다. 반려된 JSON은 최종 답변 스트림에 전달하지 않는다. 실패 결과의 `draft`는 검토용으로 남는다.

## 정상 종료 사례

`status != healthy`를 사용한 정의에서 `web-01`이 healthy인 경우다. 역조건 `status == healthy`의 빈 참 분기도 같은 조회 결과를 만든다.

```text
1) 관측 사실
- web-01: 상태=healthy, CPU=31.125%, 메모리=46.625%, 알림 0건 ...
2) 실행 경로
- 완료한 조회: 모니터링 1회, 런북 0회.
- 조건: web-01 상태, "healthy" != "healthy" → 거짓; 거짓 분기를 선택했습니다.
- 건너뜀: cpu-spike 런북; 이 단계는 조회하지 않았습니다.
- 런북을 조회하지 않았습니다.
3) 런북 요약·권고와 한계
- 조회한 런북이 없어 런북 기반 요약·권고를 생성하지 않았습니다.
```

이 경로는 `report_attempts=[]`, 보고 토큰 합계 0, 모델 호출 0회다. 자연어 정의를 생성할 때 사용한 모델·토큰과는 별개다.

보고의 조회 횟수는 완료 trace와 결과 자료를 대조한 성공 조회 횟수다. 모니터링 Tool의 `TimeoutError` 재시도나 런북 템플릿 탐색 통신까지 모두 센 값은 아니다. 예시 CPU·메모리는 고정 테스트 자료이며 현재 모의 서버가 항상 같은 값을 반환한다는 뜻이 아니다.

## 요약 실패 시 동작

조회에 성공하면 `facts_report`를 먼저 작성한다. 이후 모델 오류·거절·요약 검증 실패·보고 시간 초과가 발생해도 이 사실 보고를 보존한다. 최종 결과는 실패 상태와 기존 오류 코드를 유지하며 `report_valid=false`, `final=""`다. 화면은 “확인된 조회 결과”를 별도로 보여준다. 잘못된 요약을 확정하거나 조회 성공을 요약 성공으로 표시하지 않는다.

조회 자체가 실패하면 성공한 사실 보고를 만들지 않는다. 기존 `execution.results`와 trace에서 부분 자료·실패 위치는 확인할 수 있다.

## 검증

- **2026-10-22 재검증:** Python 전체 381개, Node 전체 46개 통과. Node는 SSE 해석 30개·Vue setup 16개다. Python 메서드 수에는 아래 34개 시나리오를 순회하는 테스트 하나가 포함된다. 실제 외부 모델 API 호출 없이 수행했다.
- 고정 입력: healthy의 `==`·`!=`, degraded, CPU 79.9·80·80.1%, 소수 정밀도·빈 분기, 실제 호출 대상·횟수 검사.
- 구조 오류: 없는 자료·문단, 새 수치, 추가 필드, 문서 중복, 빈 요약, 제어 표기를 반려하고 재작성. 반려된 모델 JSON은 `AnswerToken`으로 중계하지 않으며 최종 실패의 검토용 `draft`에만 남는다.
- 실패 경로: 모델 오류·거절·반복 검증 실패 시 사실 보고 보존, 조회 실패 시 성공 사실 미생성, JSON·SSE 응답과 UI 상태 확인.
- 기존 지원 34개 고정 시나리오의 정답 AST를 실행해 보고 경로까지 완료했다. MCP·요약은 대역을 사용하며 자연어 생성은 이 검사에 포함하지 않는다. 실제 모델의 요약 정확도 점수가 아니다. 검사 위치는 [test_workflow_eval_runner.py](../tests/test_workflow_eval_runner.py)의 `test_all_fixed_execution_scenarios_complete_with_fact_reports()`다.
- **2026-10-21 실제 로컬 Ollama 기록:** `qwen3:8b` 1건. 고정 CPU 95.2%와 프로젝트 CPU 런북으로 첫 시도 완료, 공급자 사용량 1,045토큰, 약 11.8초. 원문의 “90%를 넘고 지속되면” 전제를 요약에서 유지했다. 단일 연동 확인이며 통계적 성능 결과가 아니다. 원자료: [로컬 연동 결과](../eval/results/deterministic-report-ollama/results.json).
- 보고 계약 보완 당시와 이번 2026-10-22 문서 점검에서 OpenAI API를 호출하지 않았다. 과거 v3 평가 결과를 현재 보고 계약의 점수로 해석하지 않는다.

## 적용과 한계

백엔드와 웹 서버를 다시 시작하고 브라우저를 새로고침한다. 저장된 정의를 다시 생성할 필요는 없다. Ollama를 사용하는 경우 기존 Ollama 서버를 켜 둔다.

이 보완은 조건부 워크플로에 적용된다. 기존 일반 진단의 보고 방식이나 자동 런북 추가 정책까지 같은 검증으로 바꾼 것은 아니다.

수치 검사는 숫자의 존재를 확인하는 제한된 검사다. 같은 숫자의 다른 의미·비교 방향·기간 생략·원인 단정 등 요약의 모든 의미 오류를 판정하지 않는다. 원문의 전제조건을 유지한 문단을 함께 표시하지만 모델 요약의 완전한 사실성을 보장하지는 않는다. 다음 검증은 새 표현·문서로 요약의 조건 보존과 오탐을 측정하는 것이다.
