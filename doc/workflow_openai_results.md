# 최초 OpenAI 비교 평가 결과

<!-- [추가] 원래 실패와 수치는 보존하고 보완 후 같은 문항의 회귀 측정으로 연결한다. -->
이 문서는 보완 전 최초 측정이다. 문서 대조일은 2026-10-22이며, 수치·실패·소스 해시는 원자료의 당시 기록을 유지한다. 이후 변경·재측정은 [보완 후 회귀 평가](workflow_openai_regression_results.md)에 따로 기록한다. 현재의 [사실 출력·런북 문단 요약 계약](workflow_report_accuracy.md)에 대한 OpenAI 평가 결과는 아니다.

측정일: 2026-10-21. 사용자 승인 범위의 평가 문항·모의 카탈로그·고정 관측값·런북·실행 기록으로 `gpt-4o-mini` 생성/계획과 `gpt-4o` 보고를 실행했다. **당시 조회 경로는 개선됐지만, 의미 해석·미지원 요청 거절·보고의 사실성은 보완이 필요한 상태였다.**

## 측정 조건

지원 18문항·미지원 6문항을 dev/holdout 각각 12문항으로 나눴다. 전체 40시나리오 중 지원 시나리오는 34개다. 두 평가의 소스·문항·fixture·런북·카탈로그 해시가 같음을 확인했다. dev 실패를 본 뒤에도 코드·프롬프트를 수정하지 않았다.

소스 SHA256: `69022f59de1b128f42a342e157926e6967bde127ef61047d69d5f16368dead0b`.

실제 모델을 사용했으며 MCP는 동일 스냅샷과 원본 런북을 반환하는 프로세스 내부 대역이다. 원본 baseline의 라우팅·계획·게이트·재계획·병렬·고정 0.35초 지연은 유지했다. 생성된 워크플로는 임시 DB에 저장·다시 읽은 뒤 실행했다. 기존 사용자 DB는 사용하지 않았다.

## 핵심 결과

| 지표 | dev | holdout | 전체 |
|---|---:|---:|---:|
| 개선 방식의 절차 의미 일치 | 7/9 | 6/9 | **13/18 · 72.2%** |
| 기존 방식의 기대 경로 일치 | 5/17 | 2/17 | **7/34 · 20.6%** |
| 개선 방식의 기대 경로 일치 | 15/17 | 12/17 | **27/34 · 79.4%** |
| 기존 방식의 추가·중복 호출(지원 시나리오) | 9회 | 19회 | 28회 |
| 개선 방식의 추가·중복 호출(지원 시나리오) | 0회 | 1회 | 1회 |
| 미지원 요청의 명시적 거절 | 2/3 | 1/3 | **3/6 · 50.0%** |

최초 후보와 최종 후보의 의미 일치는 모두 13/18이었다. 당시에는 정적 구조가 유효한 의미 오류를 수정 생성 대상으로 검사하지 않았다. baseline에는 AST 의미 점수 계약이 없어 해당 점수를 만들지 않았다. 병렬 순서 영향을 제외한 호출 집합 일치는 기존 8/34, 개선 27/34였다.

미지원 6문항 중 명시적 거절 3개와 검증 실패 1개는 조회 전에 차단됐다. 나머지 **2개는 지원 범위로 잘못 바뀌어 조회가 실행됐다.** 개선 방식의 미지원 요청 도메인 호출은 총 4회였다. 위의 추가·중복 호출 표는 지원 시나리오만의 수치이므로 전체 미지원 동작까지 안전하다고 해석하면 안 된다.

지원 시나리오 중 33개는 실행·보고 형식 검증을 완료했고 1개는 지원되는 요청을 잘못 거절해 실행하지 않았다. 이 33개가 모두 사용자 의도·보고 사실성까지 정확했다는 의미는 아니다.

## 실제 발견한 실패

| 문항 | 실패 내용 |
|---|---|
| `dev_sequence` | 두 시스템을 순서대로 조회하라는 지시에 임의 `healthy` 조건 추가. 실제 degraded 관측에서 두 번째 시스템 누락 |
| `dev_three_steps` | 모니터링 → 런북 → 모니터링 순서 중 런북에 임의 상태 조건 추가 |
| `holdout_ref_second` | 두 번째 시스템 CPU 대신 첫 번째 시스템 CPU 참조, 필수 두 번째 조회를 조건 분기로 이동 |
| `holdout_six_nodes` | `>`를 `>=`로 바꾸고 양쪽 분기의 후속 모니터링 누락 |
| `holdout_runbook_only` | 지원되는 런북 순차 조회를 미지원으로 잘못 거절 |
| `dev_nested` | 미지원 중첩 조건을 명시적으로 거절하지 못함. 두 번의 생성 후 스키마 검증에서 차단, 조회 0회 |
| `holdout_restart` | 재시작 요청을 CPU 런북 조회로 바꾸어 부분 수행. `restart_service`라는 런북 노드 생성 |
| `holdout_ambiguous` | 불명확한 “CPU가 높으면 적당한 런북” 요청에 원문에 없는 `>=80`과 `cpu-spike` 도입 |

### 보고 형식 검증으로 잡지 못한 사례

`holdout_restart`의 실제 동작은 모니터링 1회와 CPU 런북 조회 1회였다. **실제 재시작은 없었지만 보고는 “서비스를 재시작하는 조치가 실행되었다”고 잘못 주장했다.** `report_valid=true`였다. 임의 노드 이름의 영향은 가능한 설명이며 이번 측정으로 원인을 입증한 것은 아니다.

`holdout_branch_monitor/boundary`는 상태·메모리·알림까지 포함한 스냅샷을 읽었지만 보고가 CPU 외 상태·지표를 확인하지 않았다고 썼다. baseline의 `dev_healthy/healthy`도 실제 런북 조회를 수행하고 답변에는 생략했다고 썼다.

따라서 `report_valid`를 사실성 검증 결과로 발표하면 안 된다. 실행한 작업과 제안한 작업, 원문 지시와 실제 생성 정의를 별도로 검증해야 한다.

## 사용량과 시간

본 비교 평가에는 공급자가 보고한 모델 호출 178회·158,067토큰을 기록했다. 별도 소규모 연동 확인은 4회·7,663토큰이며 비교 점수에 넣지 않았다. 이 문서에 해당하는 실측 합계는 182회·165,730토큰이다. 이후 v2·v3 회귀 호출은 별도 문서에 합산한다. 실제 청구 금액으로 환산하지 않았다.

| 단계 | 모델 호출 | 전체 토큰 |
|---|---:|---:|
| 기존 방식 전체 | 118 | 38,895 |
| 개선 방식 절차 생성 | 25 | 62,379 |
| 개선 방식 실행 후 보고 | 35 | 56,793 |

생성 스키마·실행 trace와 보고 길이 때문에 **호출 횟수 감소가 토큰 감소로 이어지지 않았다.** 위 표에는 미지원 요청의 처리 차이와 고정 정의의 재실행이 포함되므로 동일한 성공 작업당 비용으로 해석하지 않는다. 시나리오별·단계별 시간과 입력/출력 토큰은 원자료에 있다. 단회·고정 fixture이며 baseline 고정 지연도 있어 일반적인 속도 우월을 주장하지 않는다.

소규모 실제 연동에서는 CPU 79.9 → 메모리 런북, 80·80.1 → CPU 런북의 세 경로를 확인했다. 생성은 1회이고 저장한 정의를 관측값별로 재실행했다. 결정적 자동화 검증의 정답 AST 34/34 경로와 무효 AST 12/12 조회 전 차단도 유지된다.

## 당시 도출한 보완 사항

1. 순차 지시를 조건부로 바꾸거나 기준·대상을 임의로 추가하지 못하도록 의도 보존 검증 보강.
2. 미지원 동작을 조회로 바꾸는 부분 수행 차단과 불명확한 요청의 명시적 거절.
3. 실제 실행 trace와 보고의 완료 주장을 대조하고 허위 완료 보고 차단.
4. 원본 실패 기록을 보존한 채 개선 버전으로 재평가하고 새로운 확인 문항 추가.

초기 의미 정확도 목표 90%에는 도달하지 못했다. 당시의 성과는 기대 실행 경로 준수 개선이며, 전체 진단 정확성·완성도 확보와 구분한다. 이후 같은 문항에서의 의미·거절 보완은 [회귀 결과](workflow_openai_regression_results.md), 보고 계약 변경은 [보고 정확성 보완](workflow_report_accuracy.md)에 정리했다. 새 미관측 문항과 현재 보고 계약의 OpenAI 검증은 남아 있다.
