검토일: **2026-10-22**. 이 문서는 앞으로 직접 촬영할 화면의 안내다. 보고서의 그림 삽입 안내와 [현재 PPT](presentation/assignment1_workflow.pptx)의 캡처 1~5는 아직 실제 이미지로 교체되지 않았다. PPT의 1장 식별 정보는 `G094·임해안`이며, 나머지 페이지의 `[입력]`도 제출 전에 채운다.

보고서 첫머리의 **번호·성명**을 실제 정보로 바꾼다. 문서를 여러 페이지로 출력하면서 각 페이지에도 식별 정보를 요구받았다면 출력 도구의 머리말에 같은 번호·성명을 넣는다.

## 촬영 전 준비

1. 실제 `.env`에서 `LLM_BACKEND=openai` 또는 `ollama`를 고른다. OpenAI는 유효한 API 키를 준비하고, Ollama는 서버와 필요한 모델을 준비한다. 현재 사용 중인 백엔드와 웹 서버를 해당 터미널의 `Ctrl+C`로 종료한 뒤 아래 명령으로 각각 다시 실행한다.
2. `http://localhost:8600`을 열고 브라우저를 새로고침한다.
3. 창 크기를 넓혀 질문·분기 카드·결과가 잘 읽히게 한다. 화면에 맞추느라 글자가 작아지면 위·아래 두 장으로 나눈다.
4. 아래 순서로 촬영한다. 캡처 파일은 `doc/images/assignment1/`에 저장하면 보고서의 예시 이미지 경로와 맞는다. 해당 폴더는 촬영 파일을 저장할 때 만든다.

프로젝트 루트의 백엔드 터미널:

```bash
./.venv/bin/python3 server.py
```

별도 웹 터미널:

```bash
./.venv/bin/python3 web_demo_server.py
```

현재 [.env.example](../.env.example)은 OpenAI와 LangSmith 설정을 안내한다. 추적 화면도 촬영하려면 실제 `.env`에 `LANGCHAIN_TRACING_V2=true`, 유효한 `LANGCHAIN_API_KEY`, 사용할 `LANGCHAIN_PROJECT`를 설정한다. 같은 용도의 `LANGSMITH_*` 별칭을 중복 설정하면 우선순위에 따라 다른 프로젝트·키가 선택될 수 있다. 실제 키는 캡처에 포함하지 않는다.

브라우저에서 `http://localhost:8600/health`의 백엔드·모델 이름을 확인한 후 촬영한다. `health` 성공은 서버 설정 확인이며 외부 API 인증·모델 호출 성공을 보장하지 않는다. OpenAI를 사용하면 Ollama를 실행하지 않아도 된다. 기존 실행 셸 스크립트는 대화 DB를 삭제할 수 있으므로 캡처 준비에서는 위 직접 실행 방식을 사용한다.

모의 CPU·메모리 값은 호출마다 달라진다. 보고서 1.4절의 기존 수치는 당시 관측값이다. 새 캡처가 다른 실행이라면 본문 수치도 새 캡처에 맞춰 수정한다. 실제 조건이 참인지 거짓인지 판단한 뒤 해당 그림으로 사용한다.

최종 보고의 조회 횟수는 성공해 자료가 수집된 조회 기준이다. 일시적 모니터링 Tool 오류의 재시도나 Resource 템플릿 탐색까지 합한 원시 MCP 통신 횟수와 구분한다.

## 그림 1 — 자연어 생성과 미리보기

**질문**

```text
payments-service를 조회하고 CPU가 80% 이상이면 CPU 런북을, 아니면 메모리 런북을 확인해줘.
```

1. **조건부 워크플로** 탭에서 질문을 입력한다.
2. **절차 생성 · 실행 안 함**을 누른다.
3. 실행 전에 미리보기 화면을 촬영한다.

반드시 보이게 할 내용: 입력 질문, 대상 시스템, 조건식, CPU·메모리 런북의 양쪽 분기, **이 계획 실행** 버튼. 생성만으로 조회를 시작하지 않는 구조를 보여준다.

저장 파일: `01_preview.png`

## 그림 2 — 저장·새로고침·다시 불러오기

1. 그림 1의 절차 표시 이름을 `결제 CPU 조건부 점검`으로 정한다.
2. **이름 저장·재사용 등록**을 누른다.
3. 브라우저를 새로고침하고 조건부 워크플로 탭을 연다.
4. 왼쪽 **저장한 절차**에서 해당 이름을 선택한다. 절차를 새로 생성하지 않는다.
5. 저장 목록과 불러온 미리보기·실행 해시가 함께 보이게 촬영한다.

이후 **이 계획 실행**을 눌러 재사용을 확인할 수 있다. 같은 정의를 실행해도 관측값과 실행 ID는 새로 생긴다. 재사용은 정의를 다시 생성하지 않는다는 뜻이며 이전 실행 결과를 복구하는 기능은 아니다.

저장 파일: `02_saved_workflow.png`

## 그림 3 — 정상 상태에서 추가 조회 생략

**질문**

```text
web-01을 조회하고 상태가 healthy면 추가 조회하지 말고, 아니면 CPU 런북을 확인해줘.
```

1. 절차를 생성하고 미리보기를 확인한 뒤 **이 계획 실행**을 누른다.
2. 실행이 완료되면 조건 카드·실행 기록·확정 보고를 촬영한다.

반드시 보이게 할 내용:

- 관측 상태 `healthy`.
- CPU 런북 `skipped` 또는 “조회하지 않음”.
- 최종 보고의 **모니터링 1회·런북 0회**.
- 가능하면 사용량 영역의 **보고 모델 호출 없음 · 0토큰**. 이 값은 절차 생성 토큰과 별개다.

조건이 `status != healthy`라면 거짓 분기를 선택하는 것이 정상이다. 조건이 `status == healthy`라면 빈 참 분기를 선택할 수 있다. 두 경우 모두 최종 런북 조회가 0회인지 확인한다.

저장 파일: `03_healthy_skip.png`

## 그림 4 — 거짓 분기의 실제 런북 조회

**질문**

```text
web-01을 조회하고 CPU가 80% 이상이면 CPU 런북을, 아니면 메모리 런북을 확인해줘.
```

실행 완료 후 다음 내용을 함께 촬영한다.

- 실제 CPU가 80% 미만인 관측값과 조건 판정.
- CPU 런북 건너뜀, 메모리 런북 조회 완료.
- **모니터링 1회·런북 1회**.
- 조회한 문서 제목 **메모리 누수(Memory Leak) 대응 절차**와 원문 또는 요약.

이 화면의 핵심은 메모리 장애를 발견한 것이 아니라, 사용자가 지정한 거짓 분기의 문서를 실제로 읽었다는 점이다.

여기서 거짓 분기는 원문의 `CPU >= 80` 조건 기준이다. 생성된 정의가 동등한 역조건과 양분기 교환을 사용한다면 표시되는 참/거짓은 달라질 수 있으므로, 화면에 나온 실제 조건식과 선택 문서가 함께 맞는지 확인한다.

저장 파일: `04_false_branch.png`

## 그림 5 — 일반 진단과 비교

1. **일반 진단** 탭에서 그림 4와 같은 질문을 입력한다.
2. 질문과 응답을 함께 촬영한다.
3. 이미 관찰한 “메모리 런북 확인”과 “수집된 데이터에 메모리 런북 내용 없음” 응답이 남아 있다면 그 화면을 사용한다.

모델 응답은 재실행할 때 달라질 수 있다. 실제 화면에서 다른 결과가 나오면 그 결과를 그대로 사용하고 보고서의 비교 설명도 맞춘다. 실패 문장을 만들기 위해 답변을 편집하지 않는다. 일반 진단의 답변만으로 실제 도구 호출 횟수를 확정하지 않는다.

## 그림 6 — 최종 실행 화면

그림 2에서 저장한 **결제 CPU 조건부 점검**을 다시 불러와 실행한다. 새로 생성하지 않아도 된다.

현재 모의 자료에서는 CPU가 80% 이상인 사례로 사용한다. 촬영 시 실제 관측값이 조건을 만족하는지 확인하고, 자료를 변경했다면 선택된 런북 설명도 해당 실행에 맞춘다.

촬영할 핵심 항목:

1. 조건부 워크플로 탭과 절차 이름·입력 질문.
2. `payments-service`의 실제 CPU 관측값과 조건 판정.
3. 선택한 CPU 런북과 건너뛴 메모리 런북.
4. 실행 완료 상태와 확정 보고.
5. 런북 요약·근거 원문, 조치 전제조건, 실제 운영 조치 미수행 설명.

입력부터 결과까지 한 장에서 읽히도록 촬영한다. 세부 원문이 길면 **그림 6-1: 전체 실행 화면**, **그림 6-2: 보고·근거 원문**으로 나눠 넣는다. 위·아래 화면은 같은 실행 ID의 결과를 사용한다.

## 선택 캡처

| 선택 화면 | 촬영 내용 | 용도 |
|---|---|---|
| LangSmith trace | 실제 계측이 활성화된 실행의 단계 트리와 실행 ID·정의 해시 | LangGraph·추적 기술 설명 보강. 실제 trace가 있을 때만 첨부 |
| 자동화 테스트 | 보고서 2.6절 명령의 Python·Node 최종 통과 요약과 실행일 | 검증 결과 증빙. 2026-10-22 재검증은 Python 381개·Node 46개이며 외부 모델 연동 점수가 아님 |
| 지원 범위 오류 | “payments-service를 조회하고 서비스를 재시작해줘.” 입력 후 실제 반환된 지원 거절 | 조회 전용 범위를 설명. 실제 결과를 확인한 경우에 첨부 |

실행 중인 조사를 강제로 중단하거나 서버를 종료해 오류 화면을 만들 필요는 없다. 보고 실패 시 사실 결과 제공은 자동화 테스트로 검증했으며, 직접 촬영하지 않았다면 해당 기능의 실제 화면을 촬영했다고 쓰지 않는다.
