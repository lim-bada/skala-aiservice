## 1. 배경과 해결할 문제

현재 에이전트는 `agent/graph.py`에 고정된 진단 흐름을 사용한다. 모델이 생성하는 계획은 평면적인 작업 목록이며, 사용자가 지정한 조건부 조사 순서를 표현하고 강제하는 실행 구조가 없다.

예를 들어 “payments-service를 확인하고 CPU가 80% 이상일 때만 CPU 런북을 읽어줘”라는 지시를 받더라도, 기존 구조는 조건을 독립적인 실행 규칙으로 저장하지 않는다. `replan_check`는 수집 결과의 키워드를 기준으로 매뉴얼을 추가하며, 사용자가 확인한 계획과 실제 조회 경로를 비교하는 기능도 없다.

이를 다음처럼 개선한다.

```text
자연어 지시 → 구조화된 절차 생성 → 정적 검증 → 계획 미리보기
→ 사용자 실행 → 실제 값으로 조건 계산 → 필요한 MCP 조회
→ 실행 경로와 판단값 표시 → 최종 보고
```

AI는 자연어를 해석하고 보고서를 작성한다. 조건 계산, 도구 선택 허용 여부, 실행 순서와 횟수 제한은 코드가 담당한다. 개선 성과는 모델 자체의 추론 능력 향상이 아니라 사용자 지시의 실행 정확성과 검증 가능한 제어 구조로 설명한다.

## 2. 확정한 개선·추가 범위

| 구분 | 항목 | 구현 내용 |
|---|---|---|
| 개선 | 진단 계획 구조 | 평면 작업 목록을 순서·조건·분기를 표현하는 구조로 확장 |
| 개선 | 실행 전 검증 | 시스템·런북·필드·타입·참조·노드 수를 검사 |
| 추가 | 자연어 절차 생성 | 사용자 지시를 허용된 워크플로 JSON으로 변환 |
| 추가 | 조건부 실행기 | 조회한 값으로 조건을 계산하고 선택한 분기만 실행 |
| 추가 | 저장·재사용 | 절차를 이름으로 저장하고 다시 조회·실행 |
| 추가 | 미리보기·실행 경로 표시 | 계획, 조건값, 선택·미선택 분기, 실패 지점 표시 |
| 검증 | 자동화·전후 비교 | 조건 해석, 실제 실행 경로, 잘못된 절차 차단, 호출 수와 지연 비교 |

### 2.1 초기 지원 범위

- 순차 실행: `steps` 배열의 순서를 따른다.
- 최상위 `if/else`: 조건 노드 안에는 조회 노드만 허용한다. 중첩 조건은 지원하지 않는다.
- 허용 동작: 시스템 모니터링 조회, 장애 유형별 런북 조회.
- 조건 필드: `cpu_percent`, `memory_percent`, `status`.
- 최대 6노드: 조건 노드 자체와 실행되지 않는 분기까지 포함한 모든 노드 수를 센다. `steps` 배열과 조건식 객체는 노드로 세지 않는다.
- 최상위 `steps`는 최소 1개 노드를 포함한다.
- 최상위 모니터링 노드의 이전 결과만 조건에서 참조한다.
- 최종 보고는 실행한 자료와 trace를 근거로 생성한다.
- 저장된 절차의 재실행에서는 새로운 모니터링 값을 조회해 분기를 다시 계산한다.

### 2.2 후속 개발로 제외하는 범위

- 조사 작업 큐, 백그라운드 작업 관리, 다중 워커.
- 사용자 취소, 브라우저 재접속 시 이벤트 복원, 체크포인트 기반 중단 복구.
- 반복문, 중첩 조건, 병렬 분기, 임의 수식·Python 코드 실행.
- 서비스 재시작·롤백·확장 등 운영 상태 변경 도구.
- 로그·배포 이력 조회, RAG, 전문 Multi-Agent, 장기 요약 메모리.
- 절차의 자유 편집기, 복잡한 버전 관리, 실행 이력 관리 대시보드.

실행 결과를 구분하는 `run_id`는 trace 식별자다. 이전 후보였던 영구 조사 작업·재개 기능을 의미하지 않는다.

## 3. 대표 사용자 흐름

### 3.1 절차 생성과 실행

1. 화면에서 기존 채팅과 별도의 **워크플로 모드**를 선택한다.
2. “payments-service를 조회하고 CPU가 80% 이상이면 CPU 런북을, 아니면 메모리 런북을 확인해줘”를 입력한다.
3. 서버가 모델에 스키마와 사용 가능한 시스템·런북·필드를 전달한다.
4. 모델 출력을 파싱하고 정적 검증한다. 이 단계에서는 MCP 도메인 조회를 실행하지 않는다.
5. 검증된 계획을 임시 초안으로 저장하고 화면에 미리보기를 표시한다.
6. 사용자가 실행 버튼을 누른다. 서버는 저장된 계획을 다시 검증한 후 실행한다.
7. 모니터링 결과가 CPU 82%라면 CPU 런북만 조회한다. 메모리 런북은 실행하지 않는다.
8. 화면에 `82 >= 80 → true`, 선택한 분기, 건너뛴 단계와 최종 보고를 표시한다.

계획을 생성한 뒤 실행 직전에 LLM에게 절차를 다시 만들게 하지 않는다. 미리보기와 실제 실행이 동일한 정의를 사용해야 한다.

### 3.2 저장과 재사용

1. 유효한 초안에 이름을 붙여 저장한다.
2. 저장 목록에서 절차를 다시 연다.
3. 저장 당시 분기 결과를 재사용하지 않고 모니터링을 새로 조회한다.
4. 생성 비용을 다시 지출하지 않고 동일한 절차를 실행한다.

### 3.3 지원하지 않는 요청

- 미등록 시스템, 없는 로그 도구, 반복 조사, 시간대별 추세 등은 지원하지 않는 부분을 구체적으로 안내한다.
- 시스템이 없다고 `auth-service`로 바꾸거나 사용자가 지정하지 않은 조사를 넣지 않는다.
- 조건 기준이 불명확하면 임계값을 임의로 만들어 실행하지 않는다. 입력 수정을 요청한다.
- “정상이면 끝내줘”는 빈 분기로 표현하며 불필요한 후속 작업을 생성하지 않는다.

## 4. 워크플로 데이터 계약

작은 JSON 기반 AST를 정의하고 Pydantic 모델로 검사한다. 노드는 `type`으로 구분한다. 스키마 버전은 `1`로 시작한다.

```json
{
  "schema_version": 1,
  "name": "결제 시스템 조건부 점검",
  "steps": [
    {
      "id": "metrics_1",
      "type": "monitoring",
      "system": "payments-service"
    },
    {
      "id": "branch_1",
      "type": "if",
      "condition": {
        "ref": "metrics_1",
        "field": "cpu_percent",
        "op": ">=",
        "value": 80
      },
      "then_steps": [
        {
          "id": "cpu_book",
          "type": "runbook",
          "incident_type": "cpu-spike"
        }
      ],
      "else_steps": [
        {
          "id": "memory_book",
          "type": "runbook",
          "incident_type": "memory-leak"
        }
      ]
    }
  ]
}
```

이 예시는 총 4노드다. 실제 호출 경로에는 모니터링 1회와 선택된 런북 1회만 포함된다.

| 노드 | 필수 데이터 | 결과 |
|---|---|---|
| `monitoring` | 고유 ID, 시스템 이름 | 검증된 시스템 상태 |
| `runbook` | 고유 ID, 장애 유형 | 런북 본문 |
| `if` | 고유 ID, 조건식, 양쪽 단계 배열 | 실제 값, 참·거짓 결과, 선택 분기 |

조건 규칙:

- 숫자 필드: 유한한 숫자에 대해 `>`, `>=`, `<`, `<=`, `==`, `!=` 지원.
- 상태 필드: `healthy`, `degraded`, `down`과 `==`, `!=`만 지원.
- 문자열 숫자, 불리언을 숫자로 자동 변환하지 않는다. NaN·Infinity도 거부한다.
- `ref`는 현재 조건보다 앞에 있는 최상위 `monitoring` 노드 ID여야 한다.
- 분기 내부에서 생성한 결과를 외부 조건에서 참조하는 구조는 초기 버전에서 금지한다.
- `then_steps`와 `else_steps`는 빈 배열을 허용한다. 두 분기 모두 빈 경우는 의미 없는 조건으로 거부한다.
- 노드 ID는 전역 고유이며 정해진 짧은 식별자 형식만 허용한다.
- 스키마에 없는 키는 거부한다. 임의 도구 이름·URI·파일 경로를 모델이 지정하지 못하게 한다.

## 5. 검증기 설계

검증은 JSON 구조 검사와 실행 가능성 검사를 분리한다. 유효한 JSON이라는 사실만으로 실행을 허용하지 않는다.

| 검사 | 거부 사례 |
|---|---|
| 스키마 | 알 수 없는 노드, 누락 필드, 잘못된 타입, 추가 키 |
| 자원 | 미등록 시스템, 없는 장애 유형 |
| 조건 | 문자열 CPU 값, 상태에 숫자 비교, 허용하지 않은 필드 |
| 참조 | 중복 ID, 없는 ID, 미래 단계 참조, 다른 분기 결과 참조 |
| 구조 | 중첩 `if`, 지원하지 않는 순환·반복·제어 노드 |
| 크기 | 7개 이상 노드, 과도한 JSON 크기·문자열 길이·중첩 |

기본 입력 제한은 자연어 2,000자, 모델 출력 16KB, 절차 이름 80자로 시작하며 설정 상수로 모은다. 실행용 조건 값은 암묵적 타입 변환 없이 검사한다.

시스템·런북 목록은 `data/monitoring.json`과 `data/runbooks/`를 읽는 공통 catalog에서 만든다. 생성과 실행이 동일한 catalog를 사용하며, 실행 직전에 다시 확인한다. 저장 이후 자원이 없어졌으면 실행을 거부한다.

오류는 다음처럼 위치와 코드를 포함한다.

```json
{
  "code": "INVALID_REFERENCE",
  "path": "steps[1].condition.ref",
  "message": "조건은 앞서 조회한 최상위 모니터링 단계만 참조할 수 있습니다."
}
```

모델 출력이 구조 검사에 실패하면 오류를 전달해 최대 1회 수정 생성한다. 총 생성 시도는 2회이며 모두 비용에 포함한다. 실행 중 실패를 해결하려고 LLM이 계획을 몰래 바꾸거나 새 작업을 추가하지 않는다.

정적 검증이 자연어 의도 일치까지 보장하지는 않는다. 구조가 유효하더라도 비교 연산이나 임계값을 잘못 옮길 수 있으므로 미리보기와 별도 의미 평가가 필요하다.

## 6. 실행기 설계

실행기는 모델 출력 문장을 해석하지 않는다. 검증된 AST만 처리한다.

```text
워크플로 재검증
→ steps를 순서대로 방문
  → monitoring: 허용된 MCP Tool 조회 후 결과 검증·보관
  → runbook: MCP 서버·템플릿 탐색 후 Resource 조회
  → if: 기존 모니터링 결과로 조건 계산
       → 선택한 단계만 실행
       → 반대 분기는 skipped로 기록
→ 실행 결과·trace 생성
→ 최종 보고 생성
```

- 실행 컨텍스트는 요청별로 생성한다. 노드 결과·수집 자료·trace를 공유 전역 객체에 저장하지 않는다.
- 조건은 고정 연산자 함수 매핑으로 계산한다. `eval`, `exec`, 동적 import를 사용하지 않는다.
- 카탈로그와 동작 registry가 실제 MCP 호출 이름과 Resource 파라미터를 결정한다.
- 모니터링은 `get_monitoring_status`, 런북은 기존 `find_resource_template`와 `read_resource`를 활용한다.
- 탐색 결과는 실행 한 건 안에서 재사용할 수 있다. 데이터 조회 결과는 동일 노드가 다시 참조할 때 재사용한다.
- 조건 판단값은 그 실행에서 얻은 스냅샷이다. 이후 상태 변화까지 계속 감시하는 기능은 아니다.
- MCP 오류, `unknown`, 조건 필드 누락·타입 오류, 런북 없음은 실행 실패로 처리한다. 이를 조건의 `false`로 바꾸지 않는다.
- 실패하면 다음 노드 실행을 멈추고 오류 노드와 이미 완료한 결과를 반환한다. 성공 보고로 포장하지 않는다.
- 최대 6노드와 전체 시간 제한으로 실행을 제한한다. 실행 요청의 MCP 조회·보고 작성 전체를 기본 120초로 시작하고 실제 모델 지연을 측정해 조정한다. 생성 요청에는 별도의 모델 호출 제한을 적용한다.
- 취소·재접속 복원·서버 재시작 후 이어 실행은 제공하지 않는다. 실패 후 다시 실행하면 처음부터 새로운 실행이다.

런북 조회는 문서를 읽었다는 사실이다. 거짓 분기에서 메모리 런북을 읽었다고 해서 메모리 장애가 확인된 것은 아니다. 최종 보고는 요청에 따른 분기 선택과 실제 장애 판단을 구분한다.

## 7. 기존 LangGraph와의 연결

기존 일반 채팅·v1·v2 진단은 비교와 회귀 확인을 위해 유지한다. 새 기능은 워크플로 전용 API와 화면에서 진입한다. 기존 키워드 라우터가 워크플로 요청을 일반 대화로 보내는 문제를 피한다.

```text
기존 모드: 기존 route → plan → gate → research → replan → ...

워크플로 모드:
생성 요청 → compiler → validator → 미리보기
실행 요청 → execute_workflow → write → validate_report → finalize
```

- 새 `build_workflow_graph()`에 실행 노드와 보고 노드를 연결한다.
- 기존 `write_node`, `finalize_node`는 필요한 상태 계약을 맞춰 재사용한다. `validate_report`는 워크플로용 종료 정책을 가진 별도 노드로 만든다.
- `get_stream_writer()`를 사용하는 보고 노드를 일반 함수처럼 직접 호출하지 않고 LangGraph 실행 문맥에서 실행한다.
- 보고 입력에는 실행 경로·조건값·조회 자료를 함께 전달한다. 기존 모델의 런북/모니터링 처리와 호환되는 `collected`를 만든다.
- 기존 `replan_check`를 연결하지 않는다. 사용자가 확인하지 않은 추가 조회가 실행되지 않게 한다.
- 보고서 작성 실패와 조사 도구 실행 실패를 구분한다. 기존 `validate_node`의 3회차 강제 통과를 새 경로에 적용하지 않는다. 워크플로용 검증에서 최대 3회 작성 후에도 형식 조건을 충족하지 못하면 `report_valid=false`와 사유를 명시해 종료한다. 기본 진단 경로의 기존 정책은 유지한다.
- 자연어 생성, 검증, MCP 실행, 보고를 LangSmith에서 연결하고 `workflow_id`, `run_id`, 정의 hash를 메타데이터로 남긴다.

## 9. 모델 어댑터와 프롬프트

- 공통 서비스 계약: `await compile_workflow(query, catalog, schema, errors=None)` → 정의 후보와 사용량.
- 기존 `plan()`과 별도 메서드로 구현해 baseline의 계획 생성 로직을 바꾸지 않는다.
- 생성 결과는 데이터로만 취급하고 항상 서버 측 검증을 통과시킨다.
- 프롬프트에는 허용 문법·카탈로그·예시·지원하지 않는 요청 처리 방식을 포함한다.
- OpenAI의 현재 JSON 객체 모드만으로 필드 의미·타입이 보장된다고 가정하지 않는다. 특정 모델의 추가 출력 기능 사용 여부는 구현 시 호환성을 확인한다.
- 워크플로 생성·보고용 HTTP는 비동기로 작성한다. 특히 기존 OpenAI 보고 경로는 동기 HTTP를 호출하므로 그대로 재사용하지 않는다. 워크플로 전용 보고 어댑터를 기존 `write()` 계약에 맞춰 주입하고, 프롬프트 조립은 공통 helper로 재사용한다. 이렇게 해야 실행 전체의 시간 제한도 동작한다. 프로젝트 전체의 라우팅·계획·분석 호출 전환은 별도 필수 작업으로 확대하지 않는다.
- fake는 실행기와 오류 경로 검증용이다. 실제 자연어 이해 성능은 OpenAI로 별도 평가한다.
- Ollama의 생성 실패와 OpenAI의 생성 성능은 각각 기록한다. Ollama 처리량을 최종 성능으로 일반화하지 않는다.
- 응답의 실제 사용량 필드가 있으면 입력·출력 토큰을 나눠 기록한다. 기존 `cost_usd`는 가상 단가 기반임을 표시하며 실제 청구 금액으로 발표하지 않는다.

## 10. API와 저장 계약

| API | 역할 |
|---|---|
| `GET /workflows/catalog` | 사용 가능한 시스템·런북·필드·제한 반환 |
| `POST /workflows/generate` | 자연어를 검증된 초안으로 생성하고 저장 |
| `GET /workflows/{workflow_id}` | 미리보기용 정의·hash·메타데이터 조회 |
| `POST /workflows/{workflow_id}/save` | 이름을 지정하고 재사용 목록에 등록 |
| `GET /workflows` | 저장된 절차 목록 조회 |
| `POST /workflows/{workflow_id}/execute` | 실행 완료 후 JSON 결과와 trace 반환 |
| `POST /workflows/{workflow_id}/execute/stream` | 같은 실행 서비스를 SSE로 소비 |

`generate`는 `query`를 받고 `workflow_id`, `definition`, `definition_hash`, 검증 결과, 생성 사용량을 반환한다. 실패하면 실행 가능한 초안을 만들지 않는다.

`execute`에는 미리보기에서 받은 `definition_hash`를 전달한다. 서버는 저장된 정의를 읽고 hash 일치와 현재 카탈로그를 검사한다. 화면의 원문이나 모델을 다시 실행해 정의를 교체하지 않는다. 초안의 논리 변경은 새 ID로 재생성한다. 이름 변경은 실행 정의 hash에 영향을 주지 않는다.

검증 실패는 422, 없는 절차는 404, hash·카탈로그 변경 충돌은 409, 모델·MCP 연동 실패는 적절한 5xx와 구조화된 오류로 반환한다. 스트림 시작 후 오류는 실패 이벤트로 알린다.

저장소는 `workflow.db`를 기본으로 하고 기존 대화 DB와 분리한다. `workflows` 테이블에 ID, 이름, 원문, 스키마 버전, 불변 정의 JSON, hash, draft/saved 상태, 생성 시각을 둔다. 초안은 저장 기능과 별개로 미리보기-실행 일치 보장을 위해 저장한다.

- 실행 정의의 hash는 `schema_version`과 `steps`를 포함한 객체를 키 순서 정규화 JSON으로 직렬화해 계산한다. 표시 이름 `name`과 원문은 hash 대상에서 제외한다. 저장된 실행 정의는 수정하지 않는다.
- SQL 파라미터 바인딩을 사용한다. JSON은 저장·조회 시 스키마를 검사한다.
- 전체 실행 이벤트의 영구 저장·재생은 범위에 넣지 않는다. 한 실행의 결과에는 정의 snapshot/hash와 `run_id`를 남긴다.
- 일반 대화 이력 저장은 기존 경로를 유지한다. 워크플로 실행 결과를 대화 이력에 자동 중복 추가하지 않는다.
- 파일 DB는 서버 재시작 후에도 저장한 절차를 제공한다. 기존 스크립트의 `session.db` 삭제 정책과 별개로 새 DB를 삭제하지 않는다.

## 11. 실행 이벤트와 화면

우선 JSON 실행 결과와 trace를 완성한 뒤 POST 스트리밍을 연결한다. GET EventSource가 조회와 실행 시작을 동시에 수행하게 만들지 않는다. 자동 재접속에 따른 중복 실행을 피하고, 이번 범위에 없는 재접속 복원을 암묵적으로 제공하지 않는다.

화면은 `fetch` POST 스트림을 읽는다. 프록시도 요청 body를 전달하고 upstream 오류를 구분한다. UTF-8 문자·SSE 이벤트가 네트워크 chunk 사이에서 잘리는 경우를 처리한다.

| 이벤트 | 표시할 사실 |
|---|---|
| `WorkflowStarted` | 실행 ID, 정의 hash, 시작 |
| `StepStarted` | 시작한 노드와 대상 |
| `StepCompleted` | 결과 요약, 경과 시간, 재시도 횟수 |
| `ConditionEvaluated` | 참조 노드, 실제 값, 연산자, 기준값, 결과 |
| `StepSkipped` | 미선택 분기의 노드 |
| `WorkflowFailed` | 실패 노드, 코드, 설명 |
| `AnswerToken` / `FinalAnswer` | 보고서 조각과 확정 결과 |

이벤트를 해석된 사실과 실행 결과로 제한한다. 모델의 내부 사고 과정을 화면에 표시하지 않는다.

필수 화면은 자연어 입력, 미리보기, 저장 목록, 실행 trace 네 부분이다. 첫 버전은 재귀 카드·들여쓰기와 색상으로 분기를 표시하고 별도 그래프 시각화 라이브러리는 도입하지 않는다. 실행 전에는 MCP 조회가 없으며 실행 버튼은 유효한 계획에만 활성화한다.

## 12. 자동화 테스트와 완료 기준

### 12.1 결정적 핵심 테스트

LLM 출력과 별개로 직접 작성한 AST·고정 응답을 사용한다.

| 분류 | 필수 사례 |
|---|---|
| 순차 실행 | 두 시스템의 조회 순서와 결과 분리 |
| 숫자 조건 | CPU 79.9·80·80.1에서 `>= 80`, `> 80` 분기 |
| 상태 조건 | healthy/degraded/down의 동등·비동등 비교 |
| 분기 | true·false·빈 else, 미선택 분기의 조회 0회 |
| 크기 | 전체 6노드 허용, 7노드 거부, 양쪽 분기 포함 계산 |
| 참조 | 없는 ID, 중복 ID, 미래 단계, 분기 결과 외부 참조 거부 |
| 타입 | 문자열 숫자·bool·null·NaN·잘못된 연산자 거부 |
| 자원 | 미등록 시스템·없는 런북·지원하지 않는 기능 거부 |
| 실패 | MCP 오류·unknown·누락 필드에서 후속 실행 중지 |
| API | 미리보기 전 실행 없음, hash 불일치·카탈로그 변경 거부 |
| 재사용 | 저장·재시작·조회 후 새 fixture 값으로 반대 분기 실행 |
| 보고 | 런북 조회와 장애 확정을 구분, 보고 검증 실패 표시 |

결정적 검증기·실행기·API 테스트는 모두 통과해야 완료로 본다. 테스트는 실제 오류와 외부 관찰 동작을 검증하며 내부 함수 호출 모양만 복제하지 않는다.

### 12.2 자연어 평가

- 기본 순차, 임계값, 경계 표현, 거짓 분기, 정상 시 종료, 두 시스템, 지원하지 않는 요청을 포함한다.
- 초기 24문항을 작성한다: 지원 요청 18개, 지원하지 않는 요청 6개. 개발용과 최종 확인용을 미리 구분한다.
- 정답은 타깃·필드·연산자·기준값·분기 동작과 기대 trace로 작성한다. ID나 JSON 문자열의 완전 일치를 요구하지 않는다.
- 의미 정확도 90% 이상을 초기 목표로 두되 보장하지 않는다. 수정 생성 전·후와 지원 요청 성공률·거절 정확도를 각각 기록한다.
- 실패 문항과 원인을 숨기지 않고 결과 보고서에 포함한다.

## 13. Before/After 실험

baseline은 현재 v2 그래프다. 조건을 지원하도록 baseline을 유리하거나 불리하게 수정하지 않는다. 동일한 자연어 요청과 동일한 모니터링 fixture·런북 본문을 두 방식에 주입한다. baseline의 JSON 형식이 다르다는 이유로 실패 처리하지 않고 실제 조회와 사용자 조건 준수 여부를 평가한다.

| 지표 | 측정 방법 |
|---|---|
| 조건 해석 정확도 | 지원 문항 중 필드·연산·임계값·분기 의미가 모두 맞는 비율 |
| 실행 경로 일치율 | 주어진 fixture에서 기대한 순서·분기를 수행한 비율 |
| 금지 분기 호출률 | 실행하지 말아야 할 분기에서 발생한 도메인 조회 |
| 대상 포함률 | 요청한 시스템이 올바르게 조사된 비율 |
| 잘못된 절차 차단률 | 직접 작성한 무효 AST 중 실행 전에 거절한 비율 |
| 조회 수 | monitoring Tool, runbook Resource, 탐색용 list/prompt 호출을 분리 집계 |
| 지연·사용량 | 생성·검증·실행·보고별 시간, 모델 호출 수, 입력·출력 토큰 |

측정 조건:

1. 모니터링 난수 seed만 고정하지 않고 동일 응답 snapshot을 주입한다.
2. 인위적 0.35초 지연, 최초 강제 실패, 재시도, 모델 설정·웜업 조건을 기록한다.
3. 첫 생성+실행과 저장된 절차 재실행 결과를 나눠 보고한다.
4. 사용자의 미리보기 확인 대기시간은 서버 처리시간과 분리한다.
5. fake는 결정적 실행 정확도, Ollama는 로컬 연동, OpenAI는 최종 자연어·서비스 평가로 구분한다.
6. OpenAI 비용은 토큰 사용량을 우선 보고한다. 가상 단가의 기존 비용 필드와 실제 청구 비용을 혼합하지 않는다.
7. 결과 파일에 코드 버전 식별 정보, 모델명, fixture 버전, 입력, 생성 계획, 실제 trace, 실패 사유를 남긴다.

속도 향상은 목표가 될 수 있지만 보장하지 않는다. 계획 검증·미리보기 비용이 늘어날 수 있으며, 불필요한 조회 감소와 지시 준수 개선을 함께 제시한다.

## 14. 개발 순서와 일정

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 0. 기준선 확보 | 현재 동작·fixture·비교 문항·개발 환경 기록 | 기존 정상 대화와 진단 사례 확인 |
| 1. 실행 코어 | AST, catalog, 검증기, 실행기 | LLM 없이 수작업 절차의 분기·실패 테스트 통과 |
| 2. 모델 연결 | 공통 compiler, fake·Ollama·OpenAI 어댑터 | 자연어 → 검증된 초안, 수정 1회 제한 확인 |
| 3. API·저장 | 생성·미리보기·실행·저장·조회 | 같은 계획 실행, 저장 재사용, 오류 응답 확인 |
| 4. UI·trace | 워크플로 모드, 카드, POST 스트림 | 값·분기·건너뜀·실패를 구분해 시연 |
| 5. 평가·문서 | 자동화·실모델 비교·한계·발표 자료 | 재현 가능한 결과 표와 실패 사례 확보 |

3일 배분안:

- Day1: 오전에 schema·catalog·검증기를 확정하고, 오후에 fixture 기반 실행기를 완성한다.
- Day2: 모델·API·저장을 연결하고, 오후부터 기본 미리보기·trace 화면을 붙인다.
- Day3 오전: UI·SSE 오류 처리를 마무리하고 최종 평가·회귀 검증을 실행한다. 안내 일정의 Day3 13시 마무리를 기준으로 결과 보고서와 Git 주소를 준비한다.
- Day3 오후: 결과 해석·한계·시연 순서를 정리해 발표 자료를 완성한다.

지연되면 복잡한 시각 효과·절차 편집·부가 필터를 먼저 줄인다. 정적 검증, 조건부 실행, 저장·재사용, 미리보기, 실제 trace와 비교 결과는 유지한다. 핵심 엔진을 UI보다 먼저 검증한다.

## 16. 한계와 발표 시 설명할 내용

- 유효한 AST라도 사용자의 자연어 의도를 잘못 반영할 수 있다.
- 고정된 문법·필드·도구·노드 수만 지원한다. 범용 자동화 엔진이 아니다.
- 기존 데이터는 모의 모니터링이며, fixture의 실행 정확도가 실제 운영 장애 원인 진단 정확도를 의미하지 않는다.
- 조건은 특정 조회 시점의 값으로 계산한다. 재실행하면 데이터와 결과 경로가 달라질 수 있다.
- 저장된 계획이 유효해도 실행 시 도구나 문서가 없어질 수 있어 재검증한다.
- 검증·계획 생성·보고 작성 때문에 첫 실행의 모델 사용량과 지연이 늘 수 있다.
- 기본 보고서의 형식 검증만으로 내용의 진실성을 보장하지 않는다. trace와 수집 자료를 별도로 보여준다.
- 외부 API 요청이 중단돼도 원격 모델 계산·비용까지 즉시 중지된다고 보장하지 않는다.

발표는 **기존 조건 지시 미반영 사례 → 구조화·검증·실행 설계 → 같은 입력의 경로 비교 → 실제 수치 → 실패 사례와 제한** 순서로 구성한다.
